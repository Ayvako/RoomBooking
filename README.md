# RoomBooking

REST API для управления конференц-залами, бронированиями и дополнительными услугами.

Проект разработан на **ASP.NET Core 9** с использованием **Entity Framework Core** и **SQLite**. Архитектура разделена на отдельные слои, чтобы упростить сопровождение и дальнейшее расширение приложения.

## Возможности

API поддерживает:

* создание, получение, изменение и удаление конференц-залов;
* получение списка доступных залов на выбранный период;
* создание и получение бронирований;
* изменение времени существующего бронирования;
* отмену бронирования;
* создание, получение, изменение и удаление дополнительных услуг;
* назначение услуг конференц-залам;
* проверку конфликтов бронирований;
* автоматический расчёт стоимости аренды;
* статистические отчёты по бронированиям;
* статистику по каждому залу;
* автоматическое применение начальных данных при запуске приложения;
* централизованную обработку исключений;
* OpenAPI-документацию и Scalar API Reference.

## Модель данных

### Room

Конференц-зал содержит:

* уникальный идентификатор;
* название;
* вместимость;
* базовую стоимость аренды за час;
* список доступных услуг.

### RoomService

Дополнительная услуга содержит:

* уникальный идентификатор;
* название;
* стоимость.

Услуги реализованы как связь **many-to-many** с залами.

Одна услуга может быть доступна нескольким залам, а один зал может иметь несколько услуг.

### Booking

Бронирование содержит:

* идентификатор;
* идентификатор зала;
* период бронирования;
* итоговую стоимость;
* статус;
* выбранные услуги.

Доступны два статуса:

```text
Active
Cancelled
```

# API

Базовый URL:

```text
/api
```

## Rooms

### Получить список залов

```http
GET /api/Rooms
```

### Получить зал

```http
GET /api/Rooms/{id}
```

### Создать зал

```http
POST /api/Rooms
```

Пример:

```json
{
  "name": "Зал D",
  "capacity": 40,
  "baseHourlyRate": 1800
}
```

### Изменить зал

```http
PUT /api/Rooms/{id}
```

### Удалить зал

```http
DELETE /api/Rooms/{id}
```

### Найти доступные залы

```http
GET /api/Rooms/available
```

Параметры:

```text
StartTime
EndTime
Capacity
```

Пример:

```http
GET /api/Rooms/available?StartTime=2026-09-01T10:00:00&EndTime=2026-09-01T14:00:00&Capacity=50
```

Возвращаются залы, которые:

* соответствуют требуемой вместимости;
* не имеют активного бронирования, пересекающего выбранный период.

# Bookings

### Получить все бронирования

```http
GET /api/Bookings
```

### Получить бронирование

```http
GET /api/Bookings/{id}
```

### Создать бронирование

```http
POST /api/Bookings
```

Пример:

```json
{
  "roomId": "2aa13a7f-5631-4165-a3f4-57bad328f006",
  "startTime": "2026-09-01T10:00:00",
  "endTime": "2026-09-01T12:00:00",
  "serviceIds": [
    "2a7e9d4a-c672-4216-82a6-b4c5d34d7911",
    "642e0f8a-dab3-4aef-b75a-ccbd021755ca"
  ]
}
```

В ответ API возвращает созданное бронирование и рассчитанную стоимость.

### Изменить период бронирования

```http
PUT /api/Bookings/{id}
```

Пример:

```json
{
  "startTime": "2026-09-01T14:00:00",
  "endTime": "2026-09-01T16:00:00"
}
```

### Отменить бронирование

```http
PATCH /api/Bookings/{id}/cancel
```

Отмена изменяет статус бронирования на:

```text
Cancelled
```

Удаление записи из базы данных при обычной отмене не выполняется.

# Проверка конфликтов

Перед созданием или изменением бронирования выполняется проверка пересечения периодов.

Два бронирования считаются конфликтующими, если:

```text
existing.StartTime < requested.EndTime
AND
existing.EndTime > requested.StartTime
```

Отменённые бронирования не блокируют зал.

Например:

```text
10:00 ───────── 12:00
```

и

```text
12:00 ───────── 14:00
```

не конфликтуют.

Но:

```text
10:00 ───────── 13:00
```

и

```text
12:00 ───────── 14:00
```

конфликтуют.

# Расчёт стоимости

Стоимость бронирования состоит из:

```text
Стоимость аренды зала + Стоимость выбранных услуг
```

Стоимость аренды рассчитывается почасово, поэтому один период может проходить через несколько тарифных зон.

## Стандартные часы

```text
09:00 – 18:00
```

Используется базовая стоимость:

```text
100%
```

## Утренние часы

```text
06:00 – 09:00
```

Скидка:

```text
10%
```

Множитель:

```text
0.90
```

## Пиковые часы

```text
12:00 – 14:00
```

Наценка:

```text
15%
```

Множитель:

```text
1.15
```

## Вечерние часы

```text
18:00 – 23:00
```

Скидка:

```text
20%
```

Множитель:

```text
0.80
```

## Пример

Для зала с базовой стоимостью:

```text
2000 грн/час
```

бронирование с `12:00` до `14:00`:

```text
2000 × 2 × 1.15 = 4600 грн
```

Если дополнительно выбраны:

```text
Проєктор = 500 грн
Wi-Fi = 300 грн
```

итог:

```text
4600 + 500 + 300 = 5400 грн
```

# Валидация

API выполняет проверку входных данных.

Для залов:

* название не должно быть пустым;
* ограничена максимальная длина названия;
* вместимость должна быть положительной;
* стоимость аренды должна быть положительной.

Для услуг:

* название не должно быть пустым;
* ограничена максимальная длина названия;
* стоимость не может быть отрицательной.

Для бронирований:

* `RoomId` не должен быть пустым;
* зал должен существовать;
* `StartTime` должен быть раньше `EndTime`;
* все выбранные услуги должны существовать;
* выбранные услуги должны быть доступны выбранному залу;
* период не должен пересекаться с другим активным бронированием.

# Отчёты

API предоставляет отдельные endpoints для бизнес-аналитики.

## Общая статистика бронирований

```http
GET /api/reports/bookings
```

Можно указать период:

```text
from
to
```

Пример:

```http
GET /api/reports/bookings?from=2026-09-01T00:00:00&to=2026-09-30T23:59:59
```

Отчёт содержит:

* общее количество бронирований;
* количество активных бронирований;
* количество отменённых бронирований;
* общую выручку;
* среднюю стоимость бронирования;
* общее количество забронированных часов.

## Статистика по залам

```http
GET /api/reports/rooms
```

Поддерживает параметры:

```text
from
to
```

Для каждого зала возвращается:

* ID;
* название;
* количество бронирований;
* количество забронированных часов;
* выручка.

Эти данные позволяют оценивать загрузку залов и их финансовую эффективность.

# Обработка ошибок

В API используется централизованный middleware:

```text
ExceptionHandlingMiddleware
```

Он перехватывает исключения прикладного слоя и преобразует их в HTTP-ответы с единообразным форматом.

Пример конфликта бронирования:

```json
{
  "status": 409,
  "message": "The room is already booked for the selected period."
}
```

Пример некорректного периода:

```json
{
  "status": 400,
  "message": "Start time must be earlier than end time."
}
```

Это позволяет не дублировать обработку исключений в каждом controller.

# Dependency Injection

Регистрация зависимостей централизована в:

```text
RoomBooking.Api/Extensions/DependencyInjectionExtensions.cs
```

Регистрируются:

* `RoomBookingDbContext`;
* repositories;
* application services;
* `IPricingService`.

Например:

```text
IRoomRepository
        ↓
RoomRepository
```

и:

```text
IPricingService
        ↓
PricingService
```

Такой подход позволяет заменять конкретные реализации без изменения бизнес-логики.
